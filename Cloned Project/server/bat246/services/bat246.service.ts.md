# `server/bat246/services/bat246.service.ts`

> Core BAT246 board service: board listing/detail reads, referrer resolution, position reservations, penciling/pre-pick, placement notifications, and every manual/admin placement path (named position, AT BAT, Dugout) including Green/Gold/NoCard card awards.

**Kind:** BAT246 game module (backend) - service · **Lines:** 1537

## Purpose
BAT246 is a baseball-themed board game/MLM inside Garage. Each board (`Bat246Board`) has a Home Plate, Third Base, two Second Base slots (A/B), four First Base slots (`1stA`-`1stD`, stored as `firstBase[0..3]`), eight AT BAT slots (`atBat-0`..`atBat-7`), plus an unbounded Dugout and a POD list. This file is the "everything that is not purchase-driven entry" service: it answers the board pages, records who referred whom, and places qualified distributors onto boards when an upline, the admin (Alan K) or a reservation says so. Purchase/invite-driven entry lives in `bat246Entry.service.ts`; splitting lives in `bat246Split.service.ts`.

## How it works

### Referrer resolution (L22-L90)
`resolveBat246Ref()` decides who a user's BAT246 referrer is, in strict trust order:
1. `explicitRef` (usually a `bat246Ref` query param),
2. the user's own `Bat246Distributor.bat246RefUserId` (set once, never overwritten),
3. a `Bat246OfficeInvite` row keyed by lowercased email (written when an admin sends the "Invite to become Bat246 Distributor" email, `POST /bat246/office-invite`),
4. `fallbackRef` (a house default such as the gotobigwin.com JOIN NOW link).

`refToUserId()` accepts either a 24-hex ObjectId or an affiliate id (`aff_...`, validated with `isValidAffiliateId`, then looked up in `User.affiliateId`). A ref that resolves to the user themself is discarded. Returns `undefined` when nothing is found.

### Board reads (L110-L321)
- `POSITION_KEYS` lists the 15 card positions shown on boards (Home Plate excluded). `slotForPosition()` maps a key to the slot object.
- `withPositionSummary()` strips raw slot data from list results and attaches a `positions` array with `filled` / `reserved` (active, unexpired `Bat246PositionReservation`, with `expiresAt`) / `blank` per key.
- `getBoards()` returns open boards (`pending|active|stalled|splitting`), `getCompletedBoards()` returns `completed|split` boards (newest first). Both hide `hidden` boards unless `isAdmin`, hide `mode: "test"` boards unless `includeTest`, and optionally filter to boards where `filterEmail` appears in any slot's `playerEmail`.
- `getBoardById()` returns the full board, but returns `null` for hidden boards unless the caller's email equals the hardcoded Alan K admin email (L164), and for test boards unless `includeTest`. It enriches the board: leaderboard rows get player name, distributor id, entry number, tier earnings (`minorLeague.lbEarnings.triple|homeRun|grandSlam` via tier `T/H/G`), total BCs, cards earned and countries; every slot gets `distributorId` and `trophies` (`G/H/T`) mutated in place; hotBox rows get player name and entry number; legacy `onDeckCircle` entries are folded into `dugout` and `onDeckCircle` is returned empty.
- `setBoardHidden()` is an unguarded setter; the controller enforces the Alan-K-only check.
- `getBoardMovements()` (latest `Bat246Movement` rows by `fromBoardId`), `getPlayerById()`.

### Penciling and Pre-Pick (L323-L375)
`setPenciling()` only works before `protectionPeriodEnd`; it replaces the player's entry in `board.penciling` with a target AT BAT slot that expires after 24 hours (or removes it when `targetAbSlot` is null). `setPrePick()` does the same on `board.prePick` with no time limit.

### Reservations and upline resolution (L377-L498)
- `resolveUpline()` walks the fixed tree (AT BAT pairs -> 1st Base -> 2nd Base A/B -> 3rd Base -> Home Plate) upward until it finds an occupied slot, falling back to Home Plate; returns `null` if even Home Plate is empty.
- `reservePosition()` creates a 24-hour `Bat246PositionReservation` on an open, unfilled position; a Mongo duplicate-key error (code 11000) becomes "Position already reserved".
- `getReservations()` first bulk-expires stale active reservations for the board, then returns the active ones.
- `findDugoutTargetBoard()` (private) finds an open board where the referrer holds a "dugout-direct" slot (Home Plate/3rd/2nd A/B), preferring the board the invite pointed to. It is no longer called from anywhere in this file (see Notes).

### Auto-placement helpers (L500-L676)
- `maybeAutoPlaceFirstBaseReferral(userId, dist)` - for recruits of a 1st Base referrer: fill the referrer's first empty AT BAT pair slot (`FIRST_BASE_AB_PAIR`), else the second; if both are filled and the referrer has no Gold card, leave pending (returns false) so the referrer gets their one Gold "Approve" - unless 6+ AT BAT slots are filled, in which case overflow to Dugout; if the referrer already has a card, overflow to Dugout. On success marks the distributor `isApproved`. Any error (race) returns false.
- `maybeAutoPlaceAtBatReferral()` (private, currently unreferenced) - recruit of an AT BAT player goes to Dugout and the referrer atomically gets `cardType: "Gold"` (conditional update prevents double award), plus a Gold `Bat246SalesCredit` with card-back history.

### Gold award for the 1st Base "Approve" (L678-L804)
`maybeAwardGoldToApprover(callerUserId, placedUserId, placedAtBatPosition?)` fires after `/distributors/:userId/approve`. If the caller's 1st Base slot has `salesCredits >= 2` and no card yet, it sets `cardType: "Gold"`, pushes a hotBox entry, increments `minorLeague.cardsEarned.gold` and runs the trophy check. Fire-and-forget it writes a Gold `Bat246SalesCredit` with a card back; when the approved recruit filled an AT BAT slot covered by a different 1st Base player, that player is recorded as "stolen from" and also gets a `NoCard` sales-credit row (`countsForLB: false`).

### Placement notifications (L806-L956)
`maybeCreatePlacementNotification(userId)` runs after any qualification step completes. It requires `isOfficeMember && hasBat246Membership && hasPurchasedProduct`.
- **No active reservation:** skip if already approved or no referrer. If the user has a paid invoice for the POD product (`POD_PRODUCT_ID`), record an auto POD invite instead (`recordAutoPodInvite`) - POD entries never auto-place. Skip if already in a Dugout. Otherwise create (idempotently) a `placement_unassigned` notice for the referrer, or upgrade an existing board-less `placement` notice in place. Auto-placement on "without position" purchases was deliberately removed (comment L851-L858).
- **With reservation:** if the referrer is a 1st Base player who already has a card, the recruit goes straight to the Dugout. Otherwise `resolveUpline()` finds the upline; a notice is created only when that upline sits on 3rd, 2nd or 1st Base (never Home Plate), idempotent per board+position.

### Placement execution (L958-L1536)
- `finalizePlacement()` (private) marks the user's open notification actioned, sets `isOfficeMember` and `hasPurchasedProduct` on the distributor, and when the distributor becomes fully qualified sets `isQualified/qualifiedAt`, calls `assignDistributorId()` and re-runs `maybeCreatePlacementNotification()`. It optionally updates the reservation (status `used`, possibly moved board/position). Cleanup errors are logged, not thrown.
- `getPlacementInfo(targetUserId, { atBatOnly?, boardId? })` returns the board and free positions for the "Place on Board" modal. Board choice: explicit `boardId` override; else the reservation's board (flagging `reservedPositionStale` if that board closed); else the referrer's 1st Base board; else `bat246RefBoardId`; else the newest open board. Positions reserved by other users are excluded; `dugoutAvailable` is always true.
- `listOpenBoardsForPlacement(callerUserId)` lists open boards for the board-picker: all for admin callers (`isAdminCaller`), otherwise only boards where the caller holds any slot.
- `placeUserFromReservation(targetUserId, override?, { skipGreenCard? })` places into a reservation's position or an override. Creates the `Bat246Player` if missing (`createBat246Player`), builds the slot (entry number = `totalEntries + 1`, country origin via `resolveCountryOrigin`), writes it, creates a `Bat246PlayerBoard` row and increments `totalEntries`, then may trigger a split (`maybeTriggerSplitAfterAtBatFill`: 8/8 AT BAT on an active board -> `splitBoardPhase1`). Green Card rules: placing on 1st Base credits the 2nd Base slot above; placing on AT BAT credits the covering 1st Base slot (`salesCredits + 1`, `warpStatus = min(credits, 2)`). With `skipGreenCard` (non-admin Gold Approve) the covering 1st Base player instead gets `noCards + 1` and `cardType: "NoCard"` if they had none. AT BAT fills trigger `transferAtBatPayment` (Home Plate) and `transferAtBatPaymentToThirdBase` wallet transfers, fire-and-forget.
- `placeUserInDugout(targetUserId, boardId)` pushes a Dugout slot recording `referredBy/referredByName` from the referrer's player record, creates the `Bat246PlayerBoard` row (`dugout.<n>`), and finalizes.
- `placeUserAtPosition(notificationId, callerUserId)` is the upline "Place Now" path: only the notice's `uplineUserId` may act, the user must have all three qualification flags, and the target slot must still be empty. Same slot/credit/split/wallet logic as above (no `skipGreenCard`), then marks the notice actioned and the reservation `used`. It does not call `finalizePlacement`.

## Notes
- The Alan K admin email is hardcoded (L164), as in other BAT246 files; it is an identifier, not a secret.
- `findDugoutTargetBoard()` and `maybeAutoPlaceAtBatReferral()` are dead code since auto-placement on "without position" purchases was removed; `maybeAutoPlaceFirstBaseReferral()` is still exported and used by the backfill script.
- `placeUserFromReservation` and `placeUserAtPosition` duplicate the slot/credit logic; changes to Green Card rules must be made in both.
- None of the multi-step writes are transactional; a crash mid-placement can leave a slot written without its `Bat246PlayerBoard` row or credit. Empty-slot checks are read-then-write, so concurrent placements on the same slot can race.
- In `getPlacementInfo`, `dugoutFilled` is computed but unused.
- Terminology: these are "Green Cards" (stored as `salesCredits`/`Bat246SalesCredit` for historical reasons).
