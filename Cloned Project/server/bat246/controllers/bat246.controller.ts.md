# `server/bat246/controllers/bat246.controller.ts`

> Express request handlers for the core BAT246 game API: listing and reading boards, board setup/admin actions, split/penciling/pre-pick moves, position reservations, upline placement notifications and the distributors grid.

**Kind:** BAT246 game module (backend) — controller · **Lines:** 489 · **Mounted at:** `/bat246` (browser: `/backend/bat246`)

## Purpose
The BAT246 router (`server/bat246/routes/bat246.routes.ts`, mounted with `app.use("/bat246", bat246Routes)` in `server/app.ts`) defines many inline handlers itself, but delegates its simpler, board-centric endpoints to this controller. Each export here is a thin `(req, res)` handler: it reads params/body/query, resolves the caller from `req.user.userId` (set by `requireAuth`), calls into the BAT246 services (`bat246.service`, `bat246Admin.service`, `bat246Entry.service`, `bat246Split.service`, `bat246PodInvite.service`, `bat246BoardInvite.service`) and maps thrown error messages to HTTP status codes. The one handler with real logic of its own is `listDistributors`, which assembles the admin "distributors" grid.

## How it works

### Caller identity and admin gate
Several handlers look up the caller's email with `User.findById(userId).select("email")` and lowercase it. A hardcoded admin email constant `ALAN_K_EMAIL` (L19, the "Alan K" super-admin; the same value is duplicated in other BAT246 files by design, see the comment at L16-L18) decides admin status:
- `listBoards` passes `isAdmin` so hidden boards are only listed for that user.
- `getBoard` passes the caller email so `svc.getBoardById` returns `null` (404) for hidden boards unless the caller is the admin.
- `setBoardHidden` returns 403 for anyone else.

### Test-mode boards
`requestIsFromLocalFrontend(req)` (from `bat246TestMode.ts`) returns true only when the request's `Origin` (or `Referer`) is `http://localhost:3000`. Its result is passed as `includeTest` to `getBoards`, `getCompletedBoards` and `getBoardById`, so boards with `mode: "test"` are never served to deployed sites.

### Board reads
- `listBoards` (L21-L51): `?mine=true` filters to boards where one of the slot `playerEmail` fields matches the caller's email; with `mine=true` and no resolvable email it returns empty lists. Active (`pending/active/stalled/splitting`) and completed (`completed/split`) boards are fetched in parallel and returned as `{ boards, completed }`.
- `getBoard` (L53-L82): before reading, it checks whether the board is `active`, its protection period (`protectionPeriodEnd`) has expired, it has dugout players and an empty AT BAT slot; if so it calls `promoteDugoutAfterPP` (errors swallowed). This "lazy" promotion means simply viewing a board can mutate it. Then returns `{ board }` or 404. The same handler serves the unauthenticated `/boards/:id/public` route used by invite preview pages; there `req.user` is absent so hidden boards always 404.
- `getBoardMovements` (`?limit`, default 50), `getPlayer`, `getReservations`, `getStats` (counts all `Bat246Player` docs and qualified `Bat246Distributor` docs).

### Game actions
- `triggerSplit` → `splitBoardPhase1`; 409 when the error mentions "Concurrent", else 400.
- `updatePenciling` / `updatePrePick` → `svc.setPenciling` / `svc.setPrePick` with `{ playerId, targetAbSlot }` (`targetAbSlot` null clears it); respond with the board's `penciling` / `prePick`.
- `reservePosition` → `svc.reservePosition(boardId, position, userId, productId)`; 409 for "already reserved"/"already filled".
- `placeUser` → `svc.placeUserAtPosition(notificationId, callerUserId)`; 403 "Not authorized", 409 "already been placed"/"already filled", else 400.

### Admin / setup
- `createBoard` → `adminSvc.createBoard(userId)`; the service throws "Only the admin can create boards" for non-admins, mapped to 403.
- `searchUsers` (`?q`) → `adminSvc.searchGarageUsers` (qualified distributors only).
- `assignSlot` (`{ position, garageUserId }`) → `adminSvc.assignSlot`, then returns the refreshed board.
- `activateBoard` (optional numeric `nextHomePlatePayout`) → `adminSvc.activateBoard` (starts the 120h protection period).
- `fixDugout` → `adminSvc.promoteDugoutToAtBat`; `promoteDugoutPP` → `promoteDugoutAfterPP`.
- `addHomePlateEntry` (`{ userId, userName, userEmail, productId, saleAmount, countryResidence, countryOrigin }`, first three required besides name) → `addFromHomePlateInvite`.
- `setBoardHidden` (`{ hidden: boolean }`) → `svc.setBoardHidden`; the "Make Live / Pause Live" toggle.

### Placement notifications
`getNotifications` lists un-actioned `Bat246PlacementNotification` docs where the caller is `uplineUserId`, newest first. `markNotificationRead` sets `isRead`; `clearNotification` sets `isActioned` and `isRead`. Both updates are scoped to the caller's `uplineUserId`, so a user cannot touch someone else's notifications.

### Distributors grid — `listDistributors` (L336-L488)
Paginated (`?page`, `?limit` capped at 50, default 20) list of qualified distributors sorted by `qualifiedAt` desc, with `bat246RefUserId` populated (name/email). Steps:
1. **Resilient user data** (L356-L396): `userId` is deliberately not populated. Live users are batch-fetched; when present, the row's `userId` becomes `{ _id, ...buildUserSnapshot(user) }` and a `userSnapshot` refresh is queued; when the user was deleted, the stored `userSnapshot` is used; with neither, `userId` is `null`. Snapshot refreshes are a fire-and-forget `bulkWrite`.
2. **Board membership** (L398-L423): `Bat246PlayerBoard` docs give `isOnBoard` and a playerId→boardId fallback map (for players placed by the old Approve flow, which never set `boardPlacedBoardId`). Board `trackingNumber`s are resolved for POD-placed, board-placed and fallback board IDs.
3. **POD reconciliation** (L425-L433): rows stuck on "invited" (`podInviteSentAt` set, no `podPurchaseCompletedAt`/`podPlacedAt`) go through `reconcilePodInvitedPurchases`, which returns the user IDs that have in fact purchased.
4. **Board Entry purchase check** (L435-L452): finds paid `Invoice`s whose `lineItems.itemId` is `BOARD_ENTRY_PRODUCT_ID`. `isQualified` alone is not enough, because the separate POD purchase also qualifies a distributor.
5. **Derived fields** per row: `isOnBoard`, `podStatus` (`placed`/`purchased`/`invited`/`not_invited`), `podPlacedBoardTrackingNo`, `boardStatus` (`placed` if `isApproved` or on a board, `qualified` if they paid for Board Entry, then `invited`/`not_invited`), `boardPlacedBoardTrackingNo`, `referredByName`.
Response: `{ distributors, total, page, pages }`.

### Error handling
Every handler is wrapped in try/catch and returns `{ error: err.message }`, with 500 for reads and 400 (or the mapped 403/409) for writes.

## Interfaces
- **Endpoints served:** all under `/backend/bat246` (or `/bat246` on BACKEND_HOSTS), as listed in Exports. Every route uses `requireAuth` except `GET /boards/:id/public`.
- **Database:**
  - `Bat246Board` (model `bat246Boards`) - read; mutated indirectly by services.
  - `Bat246Player` - count.
  - `Bat246Distributor` (model `bat246Distributors`) - read; `userSnapshot` written by `bulkWrite`.
  - `Bat246PlacementNotification` (model `bat246PlacementNotifications`) - read/update.
  - `Bat246PlayerBoard` - read.
  - `User` - read.
  - `Invoice` - read (paid Board Entry invoices).
- **Request headers:** `Origin` / `Referer` decide whether test-mode boards are included.

## Notes
- **Authorization is thin.** Only `setBoardHidden` (and `createBoard`, through its service) checks for the admin. The other "admin / setup" handlers (`assignSlot`, `activateBoard`, `fixDugout`, `promoteDugoutPP`, `addHomePlateEntry`, `triggerSplit`, `searchUsers`, `getStats`, `listDistributors`) and `updatePenciling`/`updatePrePick` check nothing beyond `requireAuth` here, and the caller's identity is not passed to the services they call. Any logged-in user can therefore reach them unless the service enforces a rule. Admin gating otherwise happens only in the frontend.
- `getBoard` mutates state on read (lazy dugout promotion), including on the public, unauthenticated route.
- `listDistributors` re-imports `Bat246Board` dynamically even though it is already imported statically; this is harmless.
- `getNotifications`, `markNotificationRead` and `clearNotification` call `new Types.ObjectId(...)` on route/user IDs; a malformed ID throws and returns 500.
